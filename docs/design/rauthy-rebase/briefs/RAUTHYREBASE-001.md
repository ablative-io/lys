# RAUTHYREBASE-001: Rebase the Rauthy fork onto the newest hardened upstream release and move the pin

> **Cluster:** rauthy-rebase
> **Depends on:** DIRECTORY-002
> **Blocked by:** The trigger: a non-pre-release upstream tag above v0.36.2 whose tag commit has c44f7cac and 989f9ff9 as ancestors (git merge-base --is-ancestor), with the three guard tests present and passing there. None exists when this brief is written; the newest upstream release is v0.36.2., DIRECTORY-002 landed on lys main, checked by a test named ID001_PIN_CLONE being present under crates/lys/tests on main; deploy/identity/versions.json and docs/design/identity/reports/IDENTITY-001-deployment.md arrive with it., The fork's own chain and gate in ablative-io/rauthy, which land the guard-test commit and run the fork gate test command (just build-wasm, npm install in frontend/ and just build-ui, then just test-postgres and just test-hiqlite, from the commit's justfile) whose logs trigger-guards and candidate-suite read; it does not exist when this brief is written., A build venue holding the fork's toolchain (Rust 1.95.0 or later, edition 2024, the wasm and UI build steps upstream's code_style workflow runs) and Docker for the image, reaching the standalone install's PostgreSQL service.
> **Design anchor:**
> - ADR-003 — Everything is pegged to a human authority — A person signs in first; an agent is provisioned under that person with its own identity; the person's permissions are the ceiling and the agent holds an explicit subset; every grant says who may exercise it and who may pass it on; withdrawing the authority stops every grant derived from it. The exact delegation schema is not settled by this decision.
> - ADR-005 — The identity database is PostgreSQL, possibly on a network device — PostgreSQL is used for the identity product's database. It may be set up on one of the network devices rather than on the operator's workstation.
> - ADR-009 — People sign in through a maintained Rauthy fork of our own — Rauthy authenticates people, and its one-provider-per-user limit is changed in a fork we maintain, ablative-io/rauthy, not contributed upstream as a prerequisite. The maintained branch is ablative, created from upstream v0.36.2 commit dd61ac3c84d6b238108dc8438b53043b5177a662; the fork's main stays an untouched upstream mirror; lys pins an exact commit of ablative as the submodule vendor/rauthy. Upgrades rebase ablative onto upstream release tags only, each in its own gated row; no cherry-picks and no reset of main.
> - ADR-019 — The secrets broker lives in lys, as crates/lys-secrets; Cambium consumes it and is never its home (amends ADR-001) — The broker lives in the lys repository as the crate crates/lys-secrets, part of the standalone identity platform, built in Rust. A person installs Lys to hold secrets; Cambium reaches the broker through the door as a consumer and is never its home. Rejected: the broker inside the cambium door that ADR-001 and SECRETS-002 name, which would make Cambium a runtime a person must install to keep a credential.

## Purpose

Move the maintained Rauthy fork's ablative branch and the lys vendor/rauthy pin off v0.36.2 onto the newest upstream release that carries the authentication hardening (c44f7cac, #1696, and 989f9ff9, #1728) the identity line waits on, with our commits carried onto it unaltered and three guard tests proving the account-status, redirect and logout cases at the tag. This brief is the card IDENTITY-001 and ADR-009 call IDENTITY-002, carried by roadmap row RM-003. Where the card's words say the next hardened release, the base is the newest qualifying release read immediately before the rebase. Its gate result is the evidence the separate decision on IDENTITY-001-UPSTREAM-AUTH-STATE will need.

## Task

Written ahead of its trigger; built only once R1's trigger holds and DIRECTORY-002 has landed. Run the named steps in order: trigger-check and trigger-guards (R1), migration-numbers (R2), rebase (R3), candidate-build and candidate-suite (R4), pre-rebase-tag and ablative-push (R5), pin-move, pin-clone and earlier-clone (R7), install (R8), records (R9) and, once the lys pull request's gate has passed and the pin move has landed, guards-ref-removal (R9), which writes the gate result into the card's landing record. R6 is the reset every step after ablative-push calls on failure, so it comes directly after R5. A failure before ablative-push moves neither ablative, a pre-rebase tag nor the pin, and keeps every rauthy-rebase/<tag commit>-guards and rauthy-rebase/<tag commit> branch for inspection. Both states of the fork are covered. With no fork commits at card start, ablative becomes the tag commit plus exactly one commit adding the three guard tests, and the pin moves to that commit. With fork commits at card start (DIRECTORY-004's provider-link commit, if it has landed), ablative becomes the tag commit, then the fork commits rebased in their order, then exactly one guard-test commit on top, and the pin moves to that top commit; every fork commit must survive the rebase with its behaviour intact. The guard-test file and every fork commit belong to the fork's repository and are named with their owner, never listed as lys files. The lys pull request changes exactly four paths: vendor/rauthy, deploy/identity/versions.json, docs/design/identity/reports/IDENTITY-001-deployment.md and docs/design/identity/reports/IDENTITY-002-rebase.md. The existing data the install proof comes up against is a disposable database the card makes itself, written by the previously pinned build; the kept development database is never touched. Out of scope: lifting IDENTITY-001-UPSTREAM-AUTH-STATE and opening rows 06 and 07; moving the kept development data to the new release; renumbering DIRECTORY-004's migrations; creating the fork's own chain.

## Requirements

### R1: Record the trigger as facts, prove the guard tests at each candidate tag, and choose the newest qualifying tag

Definitions used by every requirement: the lys start commit is the lys main commit the card starts from; the upstream is the fork's GitHub parent repository; a candidate is an upstream tag above v0.36.2 whose GitHub release has prerelease false (a pre-release tag, and a tag with no GitHub release, is passed over without stopping the card); the tag commit of a tag is git rev-parse <tag>^{commit}; the fork gate test command at a commit is five steps, each taken from that commit's own justfile, run by the fork gate from the commit's checkout in this order and each recorded with its exit status: just build-wasm; npm install in frontend/, which installs from the frontend/package-lock.json the commit carries and fetches nothing that lockfile does not name; just build-ui; then, with no test argument, just test-postgres and just test-hiqlite, each kept as its own log (the test-postgres log and the test-hiqlite log of that commit). The three build steps come first because at v0.36.2 static/ and templates/html are untracked and the api crate embeds static/v1 at compile time (#[derive(Embed)] #[folder = "../../static/v1/"] in src/api/src/lib.rs), so cargo build on a fresh checkout fails before any test runs without them; upstream's pre-pr-checks recipe runs build-ui before its test recipes, and its code_style workflow runs build-wasm and build-ui first. A step that exits non-zero ends the command, and no later step runs. At v0.36.2 upstream's test-postgres recipe starts a PostgreSQL container through its postgres-start dependency, runs cargo build, starts the test backend HIQLITE=false HQL_CACHE_STORAGE_DISK=false ./target/debug/rauthy serve -c config-test.toml --test against that database, waits until localhost:8081/auth/v1/ping answers, runs HIQLITE=false cargo test and stops the backend; its test-hiqlite recipe does the same with the backend ./target/debug/rauthy serve -c config-test.toml --test on Hiqlite and runs cargo test. The integration tests under src/bin/tests run only against that started backend, which is why a bare cargo test is not the fork gate test command. Before the first run at a commit, THE SYSTEM SHALL record the recorded command git show <commit>:justfile | awk '/^(build-wasm|build-ui|test-hiqlite|test-postgres)[ :]/{p=1;print;next} p&&/^[^[:space:]]/{p=0} p' and its whole output, which is the four recipe bodies build-wasm, build-ui, test-postgres and test-hiqlite as that commit holds them, including each recipe's line starting the backend with rauthy serve -c config-test.toml --test. WHEN the card starts, THE SYSTEM SHALL, in step trigger-check, read the upstream's releases, and for each candidate resolve its tag commit and run git merge-base --is-ancestor c44f7cac826a278041f325745a7547e78654506e <tag commit> and git merge-base --is-ancestor 989f9ff9a2e18a9a3195084a86541c14f890a9e2 <tag commit>, recording each exit status. Against those names the report states: test_validate_no_backchannel_logout_uri checks that a dynamically registered client may not set a backchannel logout URI, not that a logged-out session is not revived; test_validate_dyn_redirect_uri checks which redirect URIs a dynamic client may register (https or loopback http, no wildcard), not that a code is redeemed only with the exact redirect URI it was issued for; test_wildcard_prefix_match checks matching a requested URI against a registered wildcard pattern, not the binding of a code to the redirect URI it was issued for; test_validate_csrf checks a session's CSRF header, not account status, redirect binding or logout; test_init_session_needs_exception_path_without_ip_validation checks Session::is_valid on in-memory sessions by state and path, including that a session in state LoggedOut is not valid at /, not that a logged-out session is refused being set authenticated again; test_validate_atproto_identifier and test_re_atproto_handle check atproto identifier and handle syntax; and the five clients_scim.rs tests check the JSON of SCIM group patches; none checks that an account disabled or expired between authorization and code exchange is refused at exchange.
