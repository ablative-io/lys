# The working folder: rows for the design, not built

Written by Vesper, 3 October 2026, from the folder chooser work (shas 658c70e7,
2efac013, c29f7afc, 11f379c0 and the one after). Each row is a gap that code
did not close tonight, with where the thing is kept. Nothing here is built
until it is decided.

| # | Row | Where it is kept | What follows from it |
|---|---|---|---|
| 1 | An agent has one working folder, and it is a path. The computers that may run the agent can be several. A path chosen on one computer names nothing, or something else, on another. | The folder: `working_folder` on a settings version (`crates/lys-identity-server/src/provisioning_api.rs:86-89`, set at `:268-271`). The preferred computer: `runs_on` on the same version. The allowed computers: each machine's `may_run` and `may_run_roles` in the network store. | The screens now choose the folder on the computer the start will use (the settings' computer, else the one allowed computer) and say so when neither settles it. The model itself still lets a start on another computer use a folder chosen on the first. The folder belongs to an agent on a computer, not to an agent. |
| 2 | Choosing a folder by itself is a whole new settings version. The screen reads the settings and saves them again with the folder. Every member the save takes is sent back as read, but two things the server sets itself cannot be carried: the new version is unreviewed, and its skills are pinned again at the next review. | The save body: `provisioning_api.rs:149-176`. Pins emptied on save and filled at review: `:254`, `:470`. The screen's save: `surface/identity/src/features/provisioning/working-folder.ts`. | A route that sets the folder alone, keeping the review and the pins, would make "choose a folder" change one thing. Until then choosing a folder asks for a fresh review, and reviews whatever the skills say that day. |
| 3 | A look at a computer's folders is on no record. An administrator can read folder names anywhere the runner's user can read, on any computer with a runner, and nothing says who looked, where, or when. In a hospital those names can be patients. | The route asks the runner directly and keeps no act: `crates/lys-identity-server/src/machine_folders.rs` (the session routes keep one through `runner_sessions::keep_act`). | Each look should leave a receipt: who, which computer, which folder. Whether the listing should be narrower than "anywhere the runner can read" is a decision, not a default. |
| 4 | A look that hangs, for example on a network mount that does not answer, holds one of the runner's request slots until the computer answers. The person leaving does not free it. | Each request runs on its own thread: `crates/lys-runner/src/socket/connection.rs:237`. Thirty-two slots, one kept for status and end: `connection.rs:134-135`, `socket.rs:274`. The read: `crates/lys-runner/src/folders.rs`. | Thirty-one hung looks and every ordinary act on that runner is refused `runner_dispatch_full`, while status and end still answer. No clock is the rule here, so the answer is not a timeout; it is a decision about what a look may touch. |
| 5 | Adding the first computer and an agent together cannot choose a folder first: the computer is not known to Lys until the add has run. | `surface/identity/src/features/people/AddAgent.tsx`: the chooser is given the chosen computer, and there is none yet. | The add ends at the team screen, where Start asks for the folder. It works, in two steps. |
| 6 | The folder is not required when adding an agent. | `ProfileEditor.tsx` (`ProfileFields`): the folder is sent when chosen. | An add with no folder is refused at its own start, the saved request ends, and the team screen asks. Requiring it on the form is the cleaner rule and means rewriting the add-and-run tests against a real run. |
