# HOME-002: Render a Claude Code-imported home session as a Codex 0.156.0 rollout with a kept, changed and lost account

> **Cluster:** home
> **Depends on:** HOME-001
> **Design anchor:**
> - ADR-001 — Secrets are held behind a handle the door swaps for the credential — A seat holds a short-lived handle bound to its identity. The real credential sits in the door's encrypted store and never leaves the server. The door's proxy checks SpiceDB, swaps the handle for the credential, forwards the call and writes one audit line. Built in Rust inside the door; no OpenBao unless credentials minted on demand are later needed.
> - ADR-004 — Manifold is optional and every project stands alone — The engine that starts or ends a seat is whichever one runs the agent: manifold, aion, or a customer's own. Each project in the stack works without the others; an engine without the broker reads its own pool file as it does today.
> - ADR-007 — The product starts an agent by giving its start command, never by running it — The product is not an execution engine. For the first release an agent's file gives the command that starts it on a chosen machine: the command carries the agent's identity and its handles, never a credential's value, and it is rendered from the agent's kept launch record. A started agent reports back, so the sessions screen shows what is running. A terminal inside the product, sandboxes, virtual machines and containers are later runtimes that plug in, and none is built into this product.
> - ADR-012 — A translation to another harness is rendered by lys, never that harness's own importer — A session carried to another harness is a derived record rendered by lys from the home: tool traffic carried whole as the target harness's own items, readable thinking carried, the translation announcing itself in band with its source, and an account of what was kept, changed and lost beside it. Rejected: adopting, wrapping or calling the target harness's own importer, whose output is a compaction that loses what the file held.
> - ADR-013 — A render never writes into a harness's live home; its proof runs under a scratch home — A render writes only under the target directory it is given, and a proof runs the harness with its home set to a scratch directory; the credential is supplied at launch as an environment variable read from the existing key file by path, never printed, and no auth.json or other credential file is copied. Rejected: writing the rollout and its index rows into the live Codex home, which changes the operator's own thread list.
> **Checklist:**
> - C14 — lys-home's codex-render subcommand renders a Claude Code-imported home session into a Codex 0.156.0 rollout under a target directory, and the rollout's conversation items equal those of a rollout Codex 0.156.0 wrote, apart from ids and timestamps.
> - C15 — Every text part, tool call and tool result on the context path is carried whole as a Codex message, function_call and function_call_output item; a tool result longer than 4,000 characters is carried whole; a compaction is carried as Codex 0.156.0's own compaction record with its summary whole.
> - C16 — Readable thinking is carried as assistant text and listed as changed; redacted and empty thinking is dropped and listed as lost by hash with its reason.
> - C17 — The rollout's first response item is a developer message announcing a translated context with the source session id, the lys-home version and commit, the mapping codex-0.156.0 render v1, and whether its working directory came from --cwd or the source session header, its metadata naming the kind lys.translation_marker unless Codex 0.156.0 was measured refusing to replay that kind.
> - C18 — A JSON account beside the rollout lists by entry id and block hash every kept block, every changed block with its before and after kinds and how, and every lost block or entry with its reason.
> - C19 — An authored turn is carried as assistant output behind the authored marker and an inherited entry in its own role behind the inherited marker naming its source session, both listed as changed.
> - C20 — A sidechain is carried as a spawned Codex thread in the shape 0.156.0 writes for its own when that shape is measured here, and is otherwise listed as lost with that reason.
> - C21 — A render whose rollout or account path exists is refused by that path and writes nothing; the report is JSON of paths and counts with no content.
> - C22 — Codex 0.156.0, run with a scratch Codex home, resumes the rendered rollout and answers from its content, recorded in PROOF-CODEX.md with hashes, counts and paths only.
> - C23 — The Claude Code render of the fixture session hashes the same as the hash recorded at the base commit.
> **Stories:**
> - S9 (Agent, Continues a session in another harness) — As an agent, I want my Claude Code session rendered as a Codex thread that Codex resumes with every message, tool call and result whole, so that I continue in another harness without being cut down to a summary.
> - S10 (Agent, Continues a session in another harness) — As a translated session, I want to be told in my own context that I am a translation and of which session, so that I never mistake myself for the original.
> - S11 (Tom, Judges a translation against the importer it improves on) — As Tom, I want each Codex translation to carry an account of what was kept, what changed shape and what was lost, block by block, so that the translation is measured against Codex's own importer rather than claimed.
> - S12 (Reviewer, Checks the translation proof before anything relies on it) — As the reviewer, I want the Codex resume measured on a named Codex version under a scratch home with hashes and counts recorded, so that a later version changing the shape is caught and the live Codex home is never touched.

## Purpose

The home's first cross-harness translation, one named pair and one session: a home session imported from Claude Code is rendered as a Codex rollout that Codex 0.156.0 resumes, in the shape that version writes for its own threads, with every text part, tool call and tool result carried whole, readable thinking carried as text, the thread announcing in band that it is a translation, and an account beside it naming what was kept, what changed shape and what was lost. Codex's own importer of Claude Code files is the recorded baseline: a compaction, not a copy. This brief improves on it and does not adopt it. Nothing above this translation assumes it until its proof holds.

## Task

Measure first (R1): record what Codex 0.156.0 writes and what it needs to resume, under scratch Codex homes, and take every shape from that recording, never from a source checkout. Then build the Codex profile in crates/lys-home/src/harness/codex (R2 to R6), the codex-render subcommand (R7), the comparison against the recorded rollout (R8), the account written down in RECORD.md (R9) and the resume proof (R10). In scope: one direction (Claude Code-imported home session to Codex), one version (0.156.0), one session per render. Out of scope: Codex to Claude Code; adopting or calling Codex's importer; Pi or any third harness; launching Codex through the launch template; making the Claude Code render deterministic (its random ids for multi-result tool records are a separate defect carded on its own, and this brief's fixture holds none so the hash it stands on is stable). The render writes the rollout under the target's sessions tree and writes no SQLite file: lys-home writes no other harness's database and takes no C SQLite. If R1 measures that 0.156.0 does not replay a rollout that has no state_5.sqlite and thread_history_1.sqlite rows, the index rows are a step of the proof and not of the crate: R1 records the measured answer and the exact sqlite3 statements, and R10 applies them to the scratch home before the resume. Whether Codex can be made to index a rollout it is handed is a later card's question. R1 has three stopping outcomes, each recorded by name in PROOF-CODEX.md and each returning the card to its lead with no crate file changed: 0.156.0 refusing to run without an auth.json; the recording missing a function_call with its output, a user image, a developer message or a compaction record; and a recorded key that no rule values and that 0.156.0 does not write the same in every payload of its kind, or one content part type carrying more than one content_item_kinds value. The translation marker's developer message carries the kind lys.translation_marker, never a kind Codex uses for its own developer parts, unless R1 measures 0.156.0 refusing to replay it, in which case it carries no content_item_kinds key and PROOF-CODEX.md records why. The rollout names the working directory given by --cwd, or the source session header's when --cwd is omitted and the header holds one, and the translation marker says which. A home compaction is carried as 0.156.0's own compaction record behind the carried-compaction marker. Sidechains are carried as spawned threads when R1 measured the 0.156.0 spawned-thread shape; otherwise each is named lost with that reason and carrying them is its own card.

### R2: The Codex 0.156.0 profile: the measured shape, marker texts, derived ids and the rollout's place
