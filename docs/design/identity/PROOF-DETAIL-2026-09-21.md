Supporting detail for the Rauthy and OpenFGA proof — 21 September 2026, Melbourne.

Recommendation: Rauthy v0.36.2 with Hiqlite; OpenFGA v1.21.0 with SQLite. These are pinned proof inputs, not installed services. Estimates below are engineering hours for one implementer, including tests and evidence, not measured durations or elapsed-time promises. No installation on Tom's box. Use an owner-authorized isolated scratch estate with fake records, separate credentials and no production Aion writes.

1. **Small end-to-end proof: 4 hours.** Prerequisites are a scratch host, an HTTPS origin with a fixed WebAuthn relying-party domain, a Google OAuth test client with the exact callback registered, and a test person available to approve sign-in and enroll a passkey. Venue provisioning, DNS and account-owner waiting time are outside the estimate; name a missing prerequisite rather than replacing Google or passkeys with mocks. This leg can run today once those inputs exist and does not wait for multi-provider development.

   Spend 0.5 hours bringing up the pinned services with isolated persistent directories; 1 hour creating one Rauthy person, enrolling a user-verifying passkey, and explicitly linking Google to that same account. Exercise fresh Google and local passkey login and verify the same issuer/subject and internal person ID, including the Google flow's MFA behavior. Spend 0.75 hours provisioning one confidential agent client, mapping its verified client identity to one enduring agent ID, restarting the worker and proving the ID persists. Validate token signature, issuer, audience and expiry; do not require a human mailbox or assume machine tokens contain `sub`.

   Spend 1 hour running a two-action scratch task against a fake record. Give the agent one OpenFGA grant and show action one succeeds. Pause on an explicit test barrier; delete the grant and await the write acknowledgement; release the barrier. Action two must issue a fresh `HIGHER_CONSISTENCY` check and be refused by name, with no second side effect, despite the unchanged valid token. Use notifications/barriers, no polling. Spend 0.75 hours repeating the deny/allow/revoke sequence, restarting services to check identity/grant persistence, and retaining redacted structured receipts plus the browser evidence. This proves revocation before the next action, not interruption or rollback of an already authorized action.

2. **Admission and revocation boundary: 6–10 hours.** Specify the authorization point and ordering between a grant removal and an action's admission. Make the enforcing service own that ordering; a fresh remote check alone is not atomic with the later write. Exercise both race orders, permission-service outage, duplicate messages and reconnect. Add recorded grant changes and push-driven cancellation/revalidation of active work and subscriptions, with restart reconciliation. Evidence must show which action was admitted before revocation and that later admissions and protected deliveries are refused. This step proves the design in the scratch executor before product integration.

3. **Actual application boundaries: 12–20 hours.** Introduce one shared principal/grant contract with Rust and Elixir adapters and server-owned browser sessions. Prove one protected path each in Cambium, Aion and Argus against isolated test services. Cover queued/running work, stream delivery, listing/counts and attachments; separately exercise agent discovery, contact, assignment and administration. Reject wrong-audience tokens and unauthenticated actor attribution. Produce a route inventory: representative paths passing does not mean the entire estate is migrated. Full rollout is a later sized brief.

4. **Google plus GitHub on one person: 24–40 hours, provisional.** First inventory Rauthy's federation reads/writes and migration rules; revise this estimate if the change is wider than expected. Replace the single provider binding with explicitly verified bindings and enforce unique provider identity ownership. Migrate old records without changing person IDs. Test linking, collision/concurrent linking, unlinking the final usable credential, MFA/recovery, deletion, sessions and interrupted migration. Prove Google, GitHub and passkey logins converge on the original person. Prepare an upstreamable patch; upstream acceptance time is excluded and not promised. No email-only merging.

5. **Recovery and operational handback: 8–12 hours.** Exercise backup/restore, credential and signing-key rotation, lost-device recovery, interrupted cross-store grant changes and replay. Walk Touch ID on Mac and Face ID on iPhone through WebAuthn. Measure check/list latency without inventing a pass threshold. Retain versions, model ID, principal IDs, redacted requests/results, event order and side-effect counts; name every failed or unrun leg. Review ownership and maintenance of any Rauthy patch before adoption.

Total proof envelope: **54–86 engineering hours**, excluding prerequisites, upstream waiting and full estate rollout. Deliver step 1 independently; later estimates are revised from its evidence. No execution has started. Plan-only checks: whitespace and `git diff --check`; no application tests, device walks, benchmarks or venue battery run.
