**The new sign-in journey:** Cambium → Rauthy → Google → Rauthy → Cambium. Google proves the external identity to Rauthy; Rauthy issues the token Cambium verifies. The Rauthy client has Cambium's callback, while the Google test client has Rauthy's upstream-provider callback. These are different client registrations and secrets. Read exact callback addresses from the configured scratch services; do not invent a hostname or reuse the live Google client.

**What Rauthy replaces:** the external OIDC issuer and Cambium client registration under `identity.oidc_issuer`, `identity.client_id` and `identity.client_secret_path`. Rauthy owns the Google federation and its account/passkey administration. The door already discovers OIDC authorization, token and JWKS endpoints, so it can retain that protocol boundary. It currently accepts RS256 only; configure the scratch Rauthy client's ID tokens explicitly as RS256, which Rauthy supports. Its default EdDSA tokens would fail the existing verifier.

**What Cambium keeps:** participant IDs, signing keys, history and author attribution; browser sessions, cookies, disclosure and signout; invitations and agent key-challenge enrollment; registry/wire-pass enforcement; CSRF state, nonce, issuer, audience, expiry and verified-email checks; callback host binding and return-to validation. OpenFGA and replacement machine authentication are later proof legs, not prerequisites for Google sign-in. Cambium signout remains a local session revocation; shared IdP logout is a separate integration, not automatically supplied by changing the issuer.

**Three necessary boundaries before changing the live issuer:**

1. Google API consent is currently coupled to login. `http/google.rs:215`, `:435` and `:486` use `IdentityState.oidc`, the login client ID and login secret for Drive/Calendar consent, code exchange and refresh. Give that road its own explicit Google OAuth settings/runtime; preserve existing token ownership and the connect callback. Rauthy login tokens must never be used as Google API tokens. Boot/config changes need their own file wall and default/config-documentation tests.
2. Existing people must retain their identities. `http/oidc.rs` keys bindings by issuer plus subject; Rauthy changes both. `oidc_participant.rs` only matches email for a currently unbound person, so simply switching the issuer can mint a second participant. Scratch starts empty. Before live migration, build an authenticated, explicit binding transition to the original participant, with collision/refusal and reopen tests; no email-only merge or recreation of keys/history.
3. The existing authorization request has no PKCE challenge and its token exchange has no verifier. Add S256 PKCE with an appropriate durable, single-use verifier lifecycle, then exercise Rauthy's normal PKCE configuration. This is door/store integration work; disabling PKCE is not the proposed solution. Keep the existing state/nonce checks as well.
