Shared identity and permissions: recommendation for Tom and Waffles, 21 September 2026, Melbourne.

My recommendation is Rauthy for authentication and OpenFGA with persistent SQLite for permissions, with a scoped multi-provider linking extension in Rauthy, ideally contributed upstream. Tom at 16:58 asked for a decisive choice and confirmed multiple services are acceptable. This is the proposed engineering direction, not a completed integration or upstream commitment. The earlier Keycloak and SpiceDB recommendation is superseded.

Rauthy is Rust, supplies account administration, OIDC, passkeys and machine credentials, and defaults to embedded Hiqlite storage. However, v0.36.2 stores one upstream provider per user and refuses linking another with “user is already federated”. Google and GitHub are supported provider types, but simultaneously linking both to one person is not supported by that path. Upstream-provider documentation labels the feature beta. We must resolve that requirement before choosing it; giving Tom two identities or merging accounts by email would be wrong. [Storage](https://sebadob.github.io/rauthy/getting_started/main.html), [released linking code](https://github.com/sebadob/rauthy/blob/v0.36.2/src/api/src/auth_providers.rs), [provider status](https://sebadob.github.io/rauthy/auth_providers/index.html).

Casdoor is the comparison for multiple linked providers. It is Go, supports SQLite, and its v4.7.0 user record has separate Google and GitHub identities. It supplies WebAuthn and MFA. However, its documented application credentials carry organisation-administrator authority inside Casdoor. Ordinary agents need a proved alternative with narrower authority; it is not a drop-in answer either. I checked selected source and documentation, not its complete linking or privilege boundary. [Storage](https://casdoor.ai/docs/basic/server-installation/), [user record](https://github.com/casdoor/casdoor/blob/v4.7.0/object/user.go), [machine credentials](https://casdoor.ai/docs/basic/public-api/), [WebAuthn](https://casdoor.ai/docs/how-to-connect/webauthn/).

OpenFGA supplies a stored relationship model for organisations, projects, records and agents. Its documented SQLite backend removes another database-server dependency. It remains a Go service with its own durable state; this does not establish multi-host SQLite availability. Cedar is the Rust alternative, but we would own more of the service, entity loading and administration. OpenFGA's documented change-reading API is pull-based; reliable push and revocation through our applications remain work to prove. [Storage](https://openfga.dev/docs/getting-started/setup-openfga/configure-openfga), [change API](https://openfga.dev/docs/interacting/read-tuple-changes), [Cedar inputs](https://docs.cedarpolicy.com/auth/authorization.html).

Waffles should have an enduring agent identity with rotating credentials. A new model or session must not create a new Waffles. Separately grant who may discover, contact, assign work to, or administer that agent, and what Waffles may do. Broad authority can be explicit without making every incoming message authoritative. Record both the authenticated initiator and executing agent. Rust and Elixir backends enforce the same policy service; the browser presents permitted actions without becoming the authority.

Touch ID and Apple's Face ID should use WebAuthn passkeys, with deliberate user-verification and recovery policy. Mac and iPhone flows remain untested. Casdoor's separate camera-based “Face ID” feature is not Apple's device authentication.

Lakekeeper provides useful Rust/OpenFGA integration evidence, but is an Iceberg catalogue using external identity and PostgreSQL. Lys at 38da404 supplies cryptographic primitives; I found no implemented OIDC service. [Lakekeeper authorization](https://docs.lakekeeper.io/docs/latest/authorization-openfga/), [repository](https://github.com/lakekeeper/lakekeeper).

Before adoption, an isolated proof must cover account linking and recovery, agent restart and credential rotation, issuer/audience checks, revocation during jobs and live delivery, protected lists and attachments, crash recovery across grant writes, and backup restoration. This research installed nothing and ran no integration, device, load, restoration or repository test suite. Supporting evidence is retained in RESEARCH.md.
