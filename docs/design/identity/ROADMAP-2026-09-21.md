# Lys identity, access and signing: a roadmap in small working sessions

Prepared for Tom, 21 September 2026, Melbourne. Private working proposal; not a settled Lys design, a deployment instruction or a new assignment to Waffles. Tom's direction at 18:09–18:12: spread the work over two to four weeks, favour roughly two-hour sessions, integrate as we go, and leave room to enjoy it.

## The destination

One place to manage people, enduring agents, their credentials, their access across the estate, and authority to sign. Cambium, Aion, Argus and the storage/database front end use that shared service. They continue to own their records, operations and enforcement boundaries.

Lys is the proposed product home. Keep its existing cryptographic library independently usable. Add the service and administration interface alongside it. Integrate stock Rauthy for authentication and evaluate OpenFGA for permissions. A coherent product does not require one executable or copying all upstream source into Lys. The permissions dependency is still a proposal requiring its own proof.

An estate identity survives changes of model, session, credentials and login provider. Existing Cambium participant IDs, keys and author attribution must survive adoption. Link external identities through explicit authenticated proof, never matching email alone. Signing authority has its own scope; a successful login does not authorize arbitrary signatures as that person.

## Pace and budget

A two-hour block means two hours of actual work, including its evidence and handoff. There is no assumed overnight implementation between sessions. Compilation or an unavailable operator may mean the receipt arrives later, and is shown as pending.

At one block a week, four weeks is eight engineering hours. That buys useful foundation work; it does not cover the entire estate. The existing provisional estimate for Cambium's remaining PKCE and Google credential separation alone is eight to twelve engineering hours, plus real browser verification and Google setup. We will revise that estimate after the next block.

Use the next two to four weeks as the first integration period. Continue the ordered checkpoints below at the same pace. If more blocks become welcome, pull the next one forward; do not expand a session silently to hit a calendar promise. No commitment to finish the full destination inside eight hours.

## First session: a basic system we can actually use

Target: the week beginning 21 September. Approximately two hours, starting from the existing isolated Rauthy service.

- First 15 minutes: read the binding gate receipt and check the scratch service's current version and state. Any gate finding takes precedence and is named if it consumes this session.
- Next 35 minutes: demonstrate the stock account/sign-in screen with a test person. This is the first usable identity component. It is not yet the Lys administration UI or Cambium login.
- Next 30 minutes: repeat login and restart the isolated service; show that the same account remains. Keep test secrets private and record the exact identity and outcome.
- Final 40 minutes: preserve the demonstration and evidence, then identify the smallest PKCE implementation row and its acceptance checks for the next session.

The earlier real-token proof already passed through HTTP with S256 and verified RS256. The browser and restart steps above are new acceptance work, not things that proof established. Google sign-in is added when the test client is ready; the initial demonstration can use the scratch account without it. Do not disable PKCE to make Cambium appear connected.

Stop with: a demonstrable standalone identity service, a repeatable check, and a precise next row. If the demonstration fails, keep the last working setup and record the failed step. No production issuer changes.

## The full sequence beyond that first period

| Checkpoint | Useful result | Evidence required before calling it complete |
| --- | --- | --- |
| 1. Identity service foundation | A person can use the stock account screen and return to the same account. | Browser sign-in, repeat login, isolated restart, saved instructions. |
| 2. Cambium sign-in | Cambium uses the new issuer while preserving its existing people. | Binding gate green; durable single-use PKCE; wrong verifier and replay refused; real browser round trip; old identity and history retained. |
| 3. Independent Google integration | Google API consent and refresh work even when login uses Rauthy. | Separate client registrations/settings; tests prove requests go to the correct provider; real scratch consent/refresh; migration and rollback procedure. |
| 4. One permission that works | A test person and an enduring agent can be granted access to one fake record, and lose it again. | Persistent permission store; explicit grant, deny and revocation; same principal after restart/credential rotation; unavailable service refused by name. |
| 5. First Lys service | One authenticated interface shows identities and confirmed permissions, and changes one real test grant. | Versioned principal/resource/action contract; independently protected administration; durable change identity and audit evidence; interrupted changes reconciled without duplicate effects. |
| 6. A second application, then the rest | The same principal and rule work beyond Cambium. | Start with one owner-agreed Argus test route; then Aion's test stub and the storage front end. Check each service's reads, lists/counts, writes, queued work and live delivery. Maintain an explicit uncovered-route inventory. |
| 7. Signing and operational readiness | Scoped signing and recovery can be trusted for the covered operations. | Explicit key custody/delegation rules; independent signature verification; rotation, revocation, restore and lost-credential recovery; failure during grant changes and signing; protected operational administration. |

Checkpoint four starts with a sequential grant/revoke demonstration. Before enforcing permissions in an application, settle and test the ordering between revocation and action admission. A permission check followed by a write is not automatically atomic. Record the last admitted action; do not promise rollback of an action already committed. Live delivery and running work need an explicit push/revalidation contract, not an invented polling loop.

Checkpoint five uses Aion workflows for structural administration changes and gates, according to the estate's existing rule. Define durable evidence of request, approval where required, application and failure. Do not treat an audit signature as proof that the underlying permission decision was correct.

The existing Lys wire-format document explicitly says its certificate extensions carry opaque bytes: they do not currently define permission semantics or revocation. Any new delegation/capability format needs its own settled design and version. Preserve historical verification.

## Deliberately later

The Rauthy fork for simultaneous Google and GitHub account linking comes after the stock integration is useful. It is a separate migration and maintenance project, not a rebranding step. Keep the patch narrow and an upstream update path. Passkeys, real Mac/iPhone verification and recovery must be proved before those methods become relied upon; do not imply the scratch password demonstration proves them.

Do not move all applications or existing users at once. Stable issuer URLs, subjects and credential domains need an explicit migration plan before a later Lys deployment; changing a service name is not sufficient. Production cutover, broad estate coverage and multi-host operation are separate checkpoints with their own evidence.
