The practical shape

Use two established services with different responsibilities. Keycloak answers who has authenticated. SpiceDB answers which relationships grant a particular action on a resource. Each application remains responsible for enforcing the answer. A shared Rust adapter and an Elixir adapter can share generated protocol definitions and common fixtures; they must not carry separate policy implementations. A new bespoke identity server or policy language is not proposed.

Keep Cambium's browser session boundary. The TypeScript browser calls its own backend, which makes authoritative checks. Do not give the browser the permission engine's administrative credential. A separate TypeScript backend or trusted MCP process can use a server client where appropriate. A hidden button is not an enforcement boundary.

For a first deployment I would use a private, single-region permission service backed by PostgreSQL, with separate database ownership for the identity and authorization products. This is additional operational state: backups, migrations, restoration tests, credentials and availability must have owners. Several applications on several machines do not by themselves require a multi-region database or Kubernetes. Replication and failover are a later measured deployment decision. Neither product would write directly into Cambium's store.

The Waffles story we should use as the acceptance case

Tom has one internal human identity. Google and later GitHub link to it through verified account-linking flows, not through automatic merging merely because two accounts present the same email. Waffles has one persistent agent identity and an explicit organisation/owner association. A model switch, restart or new task changes the session, not the agent's identity. Credential issuance and renewal happen through the service-identity mechanism; no agent needs its own Google mailbox. Provision one identity per enduring agent, not one human account per run.

Separate actions on the agent resource: discover, contact, assign work, administer and grant authority. Tom can deliberately grant Waffles broad estate administration while keeping discovery and contact restricted. Membership of a public channel does not grant command authority. A message's authenticated sender and a task's authorizing grant must survive every handoff, alongside the executing agent and service identity.

For a delegated task, authorization should respect the human's current grant, the agent's allowed role and the delegation's scope. Independently administered service jobs can have their own standing authority; do not confuse those jobs with impersonating the last person who messaged the agent. Removing an owner or grant must have defined consequences for existing sessions and jobs.

Restarting Cambium is a separate resource/action, such as a named service's restart operation. Its process controller must enforce that grant. If the agent still holds unrestricted host credentials and can signal the process directly, an HTTP permission check cannot make this restriction real. Aion workflows can carry the operation and receipt, while the privileged executor enforces authority. This is application integration we still have to build, even with an existing engine.

GitHub sign-in proves a linked identity; repository access is separate. For later repository automation, evaluate GitHub App installation/user tokens with their selected repositories and permissions. Do not hand every agent Tom's personal GitHub credentials. [GitHub Apps versus OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/differences-between-github-apps-and-oauth-apps), [installation token permissions](https://docs.github.com/en/rest/apps/apps).

The difficult boundaries to prove before adoption

1. Revocation: an old resource revision token does not prove that no later team removal occurred. Define the freshness required for every sensitive admission. SpiceDB's revision tokens help enforce a known lower bound; they do not replace the application's revocation contract. Even a fresh check does not make the later application mutation atomic with a concurrent revoke. Agree the operation's authorization point and test that race. [Read-after-write](https://authzed.com/docs/spicedb/concepts/read-after-write)
2. Durable changes: Haematite and the external permission store are not one transaction. Pick one owner for grants. Use recorded, idempotent reconciliation for cross-store operations, and prevent a partially applied restriction from exposing data. Do not implement two independent authoritative membership lists or a best-effort revoke that returns success early. Engine documentation explicitly discusses alternative ownership/synchronization patterns; our exact crash contract needs its own design. [Relationship ownership and writes](https://authzed.com/docs/spicedb/concepts/relationships)
3. Delivery: a relationship Watch event does not enumerate every user whose inherited access changed. Re-evaluate relevant subscriptions and check protected deliveries; handle reconnects and history-window loss. Do not claim Watch alone solves revocation or permanent audit storage.
4. Listings: protect search, pagination, counts, attachments, run logs and agent discovery, not only direct record reads. Avoid filtering only after pagination and presenting misleading counts. Measure list lookup/batch-check strategies against real shapes.
5. Failure: distinguish a denied action from an unavailable authorization authority. Refuse protected operations whose required permission cannot be established. Test an outage and partition explicitly; do not quietly continue with stale grants.
6. Credentials: enforce issuer, audience, expiry and authenticated actor attribution; scope service credentials; exercise rotation and key retirement. A valid signature alone is not authority to access every product.

Suggested isolated proof, before a build brief

Use fake records and test accounts only. Register separate Cambium, Aion and Argus audiences. Link a test human account, provision one Waffles-like service identity, and write one organisation/project/record permission model. Demonstrate an allowed reader and a denied reader, a private agent visible/contactable only to selected people, and an explicitly privileged service action. Revoke access during a queued job, a running job and a live subscription. Restart components, rotate credentials, interrupt a cross-store grant update, and prove named refusal and recovery. Measure permission-check and list latency; produce restore and operational-cost evidence. This report has not run that proof.

A package can supply login pages, account administration and the policy engine. None of the candidates can discover our business permissions or insert correct checks into every existing route automatically. That integration is the work we cannot outsource to a library.
