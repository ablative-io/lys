### ⛔ The enum renumbering — the most important uncommitted decision

The independent encoder found a **freeze-time** defect: with kinds `{domain=1, seat=2}` and
roles `{operational=1, speaks_for=2}`, **every valid pair has `kind == role`**, so an
implementation that wired label 1 to its role field and label 4 to its kind field would emit
**byte-identical output for every valid artifact** and no test or vector could catch it. It
would stay latent until a v2 introduced a differing pair, by which time every v1-era
implementation carried a silent field swap. **Not fixable by choosing a different test
vector** — it is a property of the numbering.

**Decided, and the implementing agent has been told:**

```
subject_kind:  1 = domain,        2 = seat
role:          2 = operational,   3 = speaks_for
valid pairs:   (1,2) and (2,3)     — nothing else decodes
```

Two properties this buys: no valid pair has `kind == role`, so a swap is detectable on *every*
case; and every swap produces an **invalid pair** (`(1,2)`→`(2,1)`, `(2,3)`→`(3,2)`), so it is
refused at decode rather than merely different. **Roles starting at 2 is not arbitrary and
must not be "tidied" back to 1** — that is what makes the fields distinguishable in the bytes.

### The independent vector is STALE and must be regenerated a fourth time

The round-3 vector was computed with `role = 1`. The renumbering to `role = 2` invalidates the

## ✅ THE ADVERSARIAL REVIEW RAN — outcome

**Cleared:** forgery, signature malleability, cross-format confusion, cross-kind confusion,
pair-check bypass, encode/decode divergence through every issuing entry point, and timing on all
three configured comparisons. Every forged artifact was **validly signed over a preimage the
reviewer's own independent encoder built**, so each refusal is a refusal of a cryptographically
perfect artifact rather than of a broken one — and the encoder reproduced all three golden
vectors byte-for-byte as its positive control.

Highlights: a 25-cell hand-signed `(kind, role)` matrix — only `(1,2)` and `(2,3)` accepted, in
**both** entry points, so an invalid pair cannot reach a consumer through the parse-only route.
The cap boundary is exactly as specified: 3885 accepted, 3886 refused, both sides. And the §3.3
cross-kind attack was built for real — a valid seat delegation whose seat identifier is literally
`example.test`, signed by the trusted root key — and refused by a domain verifier while a
value-only verifier would have accepted it. **The kind argument is doing real work.**

### ⛔ F1 — the worst finding was MINE, and it was written today

§1.2 said the delegated key is **not** validated as a curve point. **The shipped decoder validates
it**, and the code doing so was already committed. My justification — "the only available
validation is dalek's, which reduces `y` mod `p`" — was false: `is_usable_ed25519_public_key`
does an explicit canonical-`y` check *precisely because* dalek accepts `[0xff; 32]`.

Three lessons, and the third is the transferable one:

1. **A real finding was generalised past its subject.** `Ed25519Identity::verify` does accept
   non-canonical keys — measured, recorded, still open. Different function. "dalek is the only
   available validation" was inferred, never checked.
2. **The direction was the dangerous one**: a stranger implementing the text would **accept** what
   lys **refuses**. The sibling half of the same subsection (invalid UTF-8) matched the code;
   only this half was backwards.
3. ⭐ **A specification asserting what the code does, written without reading the code, is a
   second party that has quietly become a first one.** This document's authority is that it was
   written *before* the implementation and can disagree with it. Describing shipped behaviour from
   memory keeps that authority in the tone and loses it in substance — and it is worse than an
   ordinary error, because it is normative on the wire and no reader has cause to check it.

**Resolved by making validation normative for BOTH key slots** (F2 found `kid` unvalidated while
label 3 was, with `encoding.rs`'s stated invariant claiming otherwise — `[0xff; 32]` occupies the
slot it says cannot be occupied). Fixing the code rather than the comment.

## The adversarial review — the brief it ran against, kept for the next one

CLAUDE.md requires an adversarial review for cryptographic changes, and the last one found the
replay defect, so this is not a formality. Written down in advance so the review cannot be
graded against whatever it happens to find.

**The generalisation added exactly three things to attack**, and each has a specific question:

1. **The typed subject widened the comparison set from `{kid, origin}` to
   `{kid, subject_kind, subject_value}`.** The 32.8× timing leak was measured over two arms and
   the third has never been instrumented. Attack: does an early return on the *kind* leak, and is
   the `&`-combination actually preserved after the refactor? A behavioural test cannot see this
   — the previous round needed a thread-local counter, and a first injection placed *after* the
   signature check "passed" while proving nothing (phantom resolution).
2. **The `(kind, role)` pair check is new logic on the decode path.** Attack: is the pair
   validated *before* any field is used, or can an invalid pair reach a consumer? Is `(2,2)`
   refused as firmly as `(1,3)`? Does the pair check run on the *decode* path rather than only in
   `verify_delegation`, so `from_cose_bytes` cannot hand out an invalid pair to a parse-only
   caller?
3. **`sequence`'s partition gained the kind.** Attack: is there any path where a domain and a seat
   with colliding identifier strings share a counter? This is enforced nowhere yet — the fold does
   not exist — so the honest answer may be "prose only", and the review should say so rather than
   accept the spec's word.

**Do not let the review re-derive the enum finding as though it were new** — it is already fixed
and recorded in §0.5 consequence 4. Its job is the three items above plus whatever it finds
unprompted.

⚠️ **And the standing warning: every wire format in this crate has had a bug found by
IMPLEMENTATION rather than by review, including this one.** A clean review is therefore weak
evidence on its own; the private end-to-end run is what has actually caught things.

## Alignment with manifold — asked, unanswered

manifold **needs nothing and set no deadline**; its current behaviour is already honest. The
generalisation stands on lys's own merits plus one operator-stated future consumer.

The one open question that could still force a v2: **what a seat identifier actually looks
like** — `subject_value` is about to freeze and manifold has not specified its shape. The spec
now states that a subject value is scoped by the **authority key** rather than by a global
namespace, that `(authority key, subject value)` is the pair that must be unique, and that lys
**defines no structure for the value and will not parse one** — a delimiter inside a signed
identifier would freeze a parsing decision alongside it.
