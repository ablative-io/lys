# SECRETS-003 R2: adversarial review of the broker contract

Reviewer: Buckley, a lead seat, who did not write or commit CONTRACT.md.
Contract author: the author of commit 5a83dfa on hand/SECRETS-003, which wrote docs/design/secrets/CONTRACT.md.
Contract reviewed: docs/design/secrets/CONTRACT.md at 5a83dfa, read against docs/design/secrets/BASELINE.md and crates/lys-core/src/attestation/sign.rs at the same commit.

Each attack below is on a line starting with its id and its class in square brackets, followed by the constructed inputs, the clause that defeats it, and whether a clause must change. An attack marked "Defeated as written" needs no change. An attack marked "Change required" is not defeated by the contract as written, and names the change. The lead decides each change; this report changes no clause itself.

## Verdict

Twenty-four attacks were tried. Ten are defeated as written. Fourteen ask for a change, most of them small, before the lead accepts R2. Two of the fourteen fall on the clauses R2's acceptance names as blocking. A20 falls on the sealed-record binding clause K20: an entry's class is not in its authenticated prefix. A11 falls on K20 and the audit line clauses K22 to K25: a rollback of the whole store together with its log is not detected. Until K20 is changed for A20 and a log-head anchor is added for A11, R3, R4 and R7 stay blocked, as R2 says.

## Attacks

A1 [a replayed or forged handle] A handle issued to identity B, copied out of B's seat, presented by identity A with a presentation A signs with its own key. Defeated as written by K9: the proxy verifies against the key registered for the identity the handle is bound to, which is B's, so A's signature fails. K8 also names HandleWrongIdentity for this case, which gives two clauses and two names for one attack. Change required, small: K9 states the order of checks, which is the digest lookup (K8), then the presentation (K9), then the lease (K10), so that one attack produces exactly one named refusal and the test legs agree which name.

A2 [a replayed or forged handle] A guessed handle, 32 random bytes presented with a presentation signed by the attacker's own registered key. Defeated as written by K6 and K8: 256 bits from the secure source cannot be guessed, and an unmatched digest is refused as HandleUnknown before any presentation is weighed.

A3 [a replayed or forged handle] The handle's SHA-256 digest recovered from a copy of the store, presented in place of the handle. Defeated as written by K8: the proxy hashes what is presented, so a digest presented is hashed again and matches nothing. K22 keeps the digest out of every audit line, so the log is not a second source.

A4 [a replayed or forged handle] A raw handle stolen from B's seat memory, presented by a party that does not hold B's identity key. Defeated as written by K9: the presentation must be signed by B's registered key, so possession of the handle alone admits nothing.

A5 [a replayed or forged handle] A valid signed presentation and handle captured on the wire from B's call, replayed on a new call within 30 seconds. Change required. K9 refuses a different operation id as PresentationReplayed, but the attacker replays the same operation id, which K9 and K11 treat as a retry that gets the first outcome recorded. If that outcome carries the upstream answer, the replayer receives B's response. K11 must say that a retry's answer is the recorded outcome and its status only, never the upstream response body. The presentation must also be bound to the channel it arrives on, the local socket peer or the connection, so that a retry is accepted only from the presenter's own channel.

A6 [a replayed or forged handle] A signature over another payload B's key signed, for example an attestation of a statement another lys flow asked B to sign, reused as a presentation. Change required. K9 relies on the payload beginning with the domain string. verify_attestation_by_signer checks a COSE_Sign1 artifact, which frames every lys attestation the same way, so the domain string is the only separation. It holds only if no other path signs caller-chosen payload bytes with an identity key. K9 must state that the presentation payload is canonically encoded with length-prefixed fields, and that no lys path signs a payload beginning with `lys-secrets/presentation/v1` except the presenter's own client.

A7 [a replayed or forged handle] A prober presents a real handle id with signatures by several candidate keys, and reads which refusal comes back. Change required. K9 names PresentationUnsigned, PresentationWrongSigner and PresentationReplayed as distinct answers. verify_attestation_by_signer deliberately returns the single value InvalidSignature for a payload mismatch, an invalid signature and an unexpected signer (crates/lys-core/src/attestation/sign.rs, the doc comment above verify_attestation_by_signer), because telling a prober its signature was good but its key was wrong reveals which key the verifier holds. K9's distinct PresentationWrongSigner undoes that property, and the proxy cannot produce it from that function without a second comparison of its own. K9 should merge PresentationWrongSigner into one refusal for any presentation that does not verify. PresentationReplayed and PresentationStale are then decided only after verification, from the verified payload's operation id and timestamp.

A8 [a use spent or counted twice] Two requests for a lease's last use sent at the same instant on two connections. Defeated as written by K10: the single writer serialises the check and the append, so one is admitted and the other is refused LeaseExhausted.

A9 [a use spent or counted twice] Two broker processes started on the same store directory, for example an old process not yet gone when a new one starts, each admitting the last use. Change required. K10's single writer is stated per lease but not enforced across processes. K10 must say the broker takes an exclusive lock on the store at start and that a second broker refuses to open it by a named reason, such as StoreLocked, with its act, stop the other broker.

A10 [a use spent or counted twice] A retry sent 45 seconds after the first attempt, with a new presentation signed with the current time and the same operation id. Change required, small. K9 says the same operation id presented again within the 30 second limit is a retry. Read literally, a re-signed presentation after the limit is not a retry and could count a second use. K11 already answers from the log with no time bound. K9's sentence should say that the same operation id under the same handle and identity is always a retry under K11, whatever the time, and that the 30 second limit bounds only the presentation's timestamp.

A11 [a use spent or counted twice] The whole store directory and the whole log directory restored together from a backup taken before the lease's last use, so the use is spent again. Change required on the audit line clauses. K20's sequence check compares an entry with the store's own log, so it cannot see a rollback of both together. K23 checks each line's signature, and an older prefix of the log is still validly signed. The contract needs a log-head anchor outside both directories: the broker records the log's head, its length and last line digest, somewhere a restore of the two directories does not reach, and refuses to start by a named reason when the log is shorter than or diverges from that head. The lead chooses where the anchor lives. Until then A11 is not defeated.

A12 [a use spent or counted twice] An observer reads operation ids from the readable audit log, then sends a call under their own handle with an operation id that B's client will use next, so B's call is refused OperationIdReused. Change required. K11 refuses the same operation id under a different handle, which turns a predictable operation id into a denial of B's calls. K11 should key the retry record by handle, identity and operation id together, so another handle's use of the same id collides with nothing. It should also require operation ids of at least 128 random bits from the client.

A13 [an admitted call outliving the rule] A streaming call, an event stream held open for an hour, admitted and forwarded just before the handle is dropped. Change required. O1 lets a forwarded call finish and deliver its answer, with no bound on how long finishing takes, so a drop leaves the credential in use upstream for as long as the stream stays open. The cancellation rule should add an outcome for a call still streaming when the drop lands. It is cut at the drop, its spend so far settled, and its audit line records its own word. The lead may instead bound O1 by a stated time.

A14 [an admitted call outliving the rule] The SpiceDB relation `use` removed from B while B's call is admitted but not yet forwarded. Change required. K15 and K16 apply the cancellation rule to a dropped handle. A removed relation is not a drop, so K16 as written says nothing about a call admitted under a permit that has since been revoked. K16 should say that a removal of the use relation, and any revocation of the grant a lease counts against, is treated as a drop for every admitted call on that handle.

A15 [an admitted call outliving the rule] The broker killed after forwarding and before recording, then a retry of the same operation id sent after restart. Defeated as written by O3 and K11: the restart appends outcome_unknown, keeps the use and reservation counted, and the retry gets outcome_unknown and is never forwarded again.

A16 [a credential in a log] An upstream error body that echoes the request's authorization header back, logged by the proxy as the error's text. Defeated as written by K1, which forbids any credential byte in a log line or an error, and by SEC3_PROXY_CANARY. The canary leg must include an upstream that echoes its request headers into its error body, or the clause is untested on its likeliest path. No clause change, but a leg input to add.

A17 [a credential in a log] A panic inside the proxy while a credential is held, printing a backtrace and the values in scope. Defeated as written by K1: every credential byte lives in the redacting type, whose Debug prints no byte, so a panic message that formats it prints none. A core dump of the process remains outside this contract, and the lead may want the broker to refuse core dumps at start. That is not required for R2.

A18 [a sealed key read] A key file supplied as a path outside the store directory that is a symbolic link into the store directory, or a log directory that is a symbolic link to the key file's directory. Change required, small. K3 refuses a key file inside either directory, but a comparison of the paths as given passes a link. K3 should say the comparison is made on canonical paths, with every link resolved, for the key file and for both directories.

A19 [a sealed key read] The broker killed during a store-key rotation, after some entries are resealed to the new key and before the rotation's audit line. Change required. K5 says the old key stays current until the audit line, and that resealed entries are not read, but not what the broker does at the next start with a store half resealed. A resealed entry opened with the old key fails, and an unresealed entry opened with the new key fails. K5 should say a restart either finishes the rotation or discards the resealed copies, keeping both sealings of an entry until its rotation line is appended. It should name the refusal for a store found in that state.

A20 [a sealed key read] A key-class entry's class changed to memory-class in the store's record of the entry, with its ciphertext left intact, then read as a memory record. Change required on the sealed-record binding clause. K21 refuses a read of a key-class record, but K20's authenticated prefix carries the entry id, name, owner and sequence and not the class. A class held outside the sealed plaintext can be changed without breaking the seal, and the read then returns the key. K20's prefix must include the entry's class, and opening must refuse by EntryBindingMismatch when the recovered class differs from the class the read asked under.

A21 [a sealed key read] A store entry's ciphertext swapped with another entry's, both owned by B. Defeated as written by K20: the recovered entry id and name differ from the entry being read, refused EntryBindingMismatch, no plaintext returned.

A22 [a sealed key read] An older ciphertext of the same entry restored in place of its current one, with the store's log left current. Defeated as written by K20: the recovered sequence is older than the latest the log records for that entry, refused EntryRolledBack naming the entry and its act. This is the rollback attack R2 requires, and K20's sequence is the clause that defeats it while the log is current. A11 covers the case where the log is restored too.

A23 [a stale SpiceDB answer] A permit read from SpiceDB before B's relation was removed, used for a call after the removal. Defeated as written by K19 as far as the landed DIRECTORY-006 R4 check goes, and K19 rightly does not choose that check's behaviour. Change required, small: K17 should say the broker keeps no permit of its own beyond what the DIRECTORY-006 R4 check allows, so no broker-side cache outlives the freshness mechanism K19 defers to.

A24 [a stale SpiceDB answer] SpiceDB unreachable when a call arrives, so no answer is returned at all. Defeated as written by K17: any answer that is not a permit is refused as PermissionDenied and nothing is forwarded, so an absent answer denies.

## Changes asked of the contract

K8 and K9, the order of checks and one name per attack (A1). K9, the canonical presentation encoding and the only signing path (A6). K9, one refusal for any presentation that does not verify (A7). K9, a retry is decided by K11 at any time (A10). K10, the exclusive store lock (A9). K11, the retry answer carries no response body and is bound to the presenter's channel (A5), and the retry record is keyed by handle, identity and operation id (A12). K16, a streaming call at the drop (A13) and a revoked relation treated as a drop (A14). K3, canonical paths (A18). K5, restart during rotation (A19). K17, no broker-side permit cache (A23). K20, the class in the authenticated prefix (A20). The audit line clauses, a log-head anchor outside the store and log directories (A11).

A16 asks for a leg input, not a clause change.
