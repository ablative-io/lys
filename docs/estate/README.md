# The estate permission plan, 29 September 2026

This is a sourced, bounded first import: nine real Cambium channels/topics, aion's `default` namespace, three non-model source workflows, and the Lys Git repository. It contains 15 resource-grant rows and 70 seat delegations. It excludes direct messages, paid model workflows, unknown app installations and unsourced repository rights. Each row carries its evidence. The six seat display names are those already imported on Tom's installation.

These are **new explicit Lys grants proposed to Tom**, reflecting observed work and existing authority. They are not proof that Cambium/aion currently enforce through Lys. Cambium presently uses WorkspaceOpen; aion's live `/whoami` answers shared auth-off operator access. No per-seat aion credentials are claimed. Read/run labels describe the existing operations; the declared schema does not silently reconfigure either application. The grant graph records what Tom explicitly delegates here.

Resource IDs are token-safe labels for current channel/topic names and namespace/workflow names: lowercase, with dots or hyphens in place of separators. Each Cambium evidence line retains the exact stream ID; names are snapshot resource keys for this initial registration, not a claim that Cambium routes by name or that a rename updates Lys. The repository token github.com.ablative-io.lys identifies the Git remote https://github.com/ablative-io/lys. The app schemas are declarations for Tom to approve, derived from these operations, not exported production Lys bindings from either app.

## The product steps

1. From the checkout containing this directory, run `lys identity import docs/estate/apps.json --json`. This registers Cambium and aion as pending. It does not approve them. If either app already exists, stop and compare its current schema; do not overwrite it or invent a different app ID.
2. Tom opens `http://localhost:8490/#/apps`, reads both schemas and chooses **Approve Cambium** and **Approve aion**. Their new credentials are shown once by the product; keep them private. These credentials alone do not switch the running apps' authentication.
3. In `http://localhost:8490/#/directory/manage?action=status`, use **Change status**, choose each of the six Registered agents, choose **activate**, and **Record change**. Already active agents need no act. No importer performs this step.
4. Open `http://localhost:8490/#/access/import`. The page loads the plan placed at `data/estate-approval.json` by install/upgrade and validates its resource tokens before showing approval. Opening writes nothing. Read the resources, actions, recipients and evidence, then choose **Approve and apply estate grants**. Roots are held by the signed-in administrator; ordinary delegations let the installed loader pass only these actions to the listed agents.
5. The product applies the grants through the real installed loader credential. No credential, picker, download or CLI is involved. Existing agent registration operations and source grant IDs remain the same, so explicit repetition reconciles the same operations. The server checks administrator access and that the loader belongs to that person; every import entry rechecks the loader's ordinary grants. Roots cannot be issued by the loader.
6. Open `http://localhost:8490/#/resources` and `http://localhost:8490/#/graph`. The page reports completion only after confirming every planned import entry. An uncertain response stops without automatic retry; earlier grants can already be recorded. All roots and delegations remain revocable.

Waffles reported that Tom approved and imported the estate at 10:54 on 29 September. That is the prior flow's live report, not proof of this replacement flow. This revision requires the updated identity service and installer alongside the surface.
