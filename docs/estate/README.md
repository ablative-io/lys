# The estate permission plan, 29 September 2026

This is a sourced, bounded first import: nine real Cambium channels/topics, aion's `default` namespace, three non-model source workflows, and the Lys Git repository. It contains 15 resource-grant rows and 70 seat delegations. It excludes direct messages, paid model workflows, unknown app installations and unsourced repository rights. Each row carries its evidence. The six seat display names are those already imported on Tom's installation.

These are **new explicit Lys grants proposed to Tom**, reflecting observed work and existing authority. They are not proof that Cambium/aion currently enforce through Lys. Cambium presently uses WorkspaceOpen; aion's live `/whoami` answers shared auth-off operator access. No per-seat aion credentials are claimed. Read/run labels describe the existing operations; the declared schema does not silently reconfigure either application. The grant graph records what Tom explicitly delegates here.

Names are the actual current channel/topic names and namespace/workflow names. Each Cambium evidence line retains the exact stream ID; names are snapshot resource keys for this initial registration, not a claim that Cambium routes by name or that a rename updates Lys. Repository names are the Git remote. The app schemas are declarations for Tom to approve, derived from these operations, not exported production Lys bindings from either app.

## The product steps

1. From the checkout containing this directory, run `lys identity import docs/estate/apps.json --json`. This registers Cambium and aion as pending. It does not approve them. If either app already exists, stop and compare its current schema; do not overwrite it or invent a different app ID.
2. Tom opens `http://localhost:8490/#/apps`, reads both schemas and chooses **Approve Cambium** and **Approve aion**. Their new credentials are shown once by the product; keep them private. These credentials alone do not switch the running apps' authentication.
3. In `http://localhost:8490/#/directory/manage?action=status`, use **Change status**, choose each of the six Registered agents, choose **activate**, and **Record change**. Already active agents need no act. No importer performs this step.
4. Open `http://localhost:8490/#/access/import`. Choose `docs/estate/approval-plan.json`. Loading reads and previews; it writes nothing. Select **Lys directory loader**, read the exact resources/actions/recipients and their evidence, then Tom chooses **Approve these roots and delegate to my loader**. The existing grant API checks Tom as administrator. Each root is held by Tom; a matching ordinary delegation gives the loader only that resource and actions, with pass-on to agents. Roots and loader grants have no expiry of their own; both remain revocable. No root request is made under the loader's bearer.
5. The page downloads `estate-grants.json`, populated with the actual source-grant IDs returned by the product. Run `lys identity import ~/Downloads/estate-grants.json --json`. It resolves the already imported agents by repeating their original content-addressed registration operations, then delegates from those explicit source grants. The document's grants are use-only.
6. Open `http://localhost:8490/#/resources` and `http://localhost:8490/#/graph`. Read the actual results; a refusal is not success. The page/CLI stops at an uncertain response and never automatically retries. Some earlier grants may already exist. An explicit repetition uses the same content-derived operation IDs for the same plan, selected loader and Tom identity.

The approval page is source written for the owner build. It has not been typechecked or exercised live yet. Do not call the entire estate loaded merely because the six registrations succeeded. The latest observed successful registration is Waffles' 10:35 report for combined build 5d293f8f. Root approval and usable grant import remain separate acts.
